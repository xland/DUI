# 决策清单（ADR）

> 状态：ADR-001 / 003 / 005 / 009 / 010 / 016 / 018 已定；其余 **待定**，括号内为我的草案建议，供讨论时直接确认或推翻。
> 影响维度缩写：`体`=二进制体积，`内`=内存占用，`性`=运行时性能，`复`=实现复杂度。

---

## ADR-001 渲染后端：D3D11 还是 D3D12

| 方案 | 影响 | 说明 |
| --- | --- | --- |
| **D3D11**（建议） | 体+++ 内+ 性○ 复+++ | 驱动成熟、代码量小、兼容性覆盖全 Win10；GUI 负载下 CPU 开销完全够用 |
| D3D12 | 体--- 内+ 性++ 复--- | 需自行管理命令列表、栅栏、描述符堆、资源屏障；代码量成倍增长 |

**已定：D3D11。** D3D12 的收益（减少驱动开销）在 GUI 场景体现不出来，代码量成倍增长。

## ADR-002 绘制原语的着色方式

| 方案 | 影响 | 说明 |
| --- | --- | --- |
| 实例化 quad + 参数化像素着色（建议） | 体++ 内++ 性+ 复○ | 每个图元一个 instance（矩形/圆角矩形/边框/渐变/图片共用一个 shader），顶点量极小，圆角与边框用 SDF 在像素级求值，天然抗锯齿 |
| CPU 三角化 | 体+ 内-- 性-- 复+++ | 圆角需按半径细分，顶点数随复杂度增长，且需为每个圆角生成/缓存顶点 |
| Direct2D | — | 与"仅 D3D + DWrite"的目标冲突，且引入 D2D/DXGI 目标绑定复杂度 |

**建议：实例化 quad + 单像素着色器（含少量分支或按图元类型的多 shader 变体）。**

## ADR-003 文本光栅化方式

| 方案 | 影响 | 说明 |
| --- | --- | --- |
| **每缩放档 Alpha 图集**（建议起步） | 体+++ 复+++ | `CreateGlyphRunAnalysis` + `CreateAlphaTexture` 直接得到灰度/子像素位图；代码最少。代价：每个 (字号 × 缩放档) 一份图集，缩放档多时内存上升，非档位缩放会糊 |
| 轮廓三角化 + 解析式 AA | 体-- 复--- | `IDWriteFontFace::GetGlyphRunOutline` 取轮廓 → 三角化 + 覆盖像素着色；无级缩放质量最高，但需要完整 tessellator |
| SDF 图集 | 体○ 内++ 性○ 复○ | 每字形仅需一份小尺寸 SDF，任意缩放与旋转都清晰，但需要距离场生成代码（约数百行） |

**已定：Alpha 图集 + 缩放变化时重新光栅化。**

- 接口抽象为"按 (字体/字形, 像素尺寸) 取字形位图"，图集带容量上限与 LRU 淘汰。
- DPI / 字号 / 变换缩放均视为**离散事件**：按新尺度重新光栅化并更新缓存，不做跨尺度复用采样（复用才糊）。
- 超大字号可退化为轮廓绘制避免位图过大（阈值实现时定）。
- 行业对照：Qt Widgets、Skia/Avalonia（曾有 SDF 路径后移除）、Direct2D/WinUI3 均为此路线；SDF 是 Qt Quick / 游戏引擎的连续缩放方案，DUI 未来若出现画布类无级缩放需求再引入。

另需确定（待定）：是否支持子像素（ClearType）——子像素与"任意合成/半透明"冲突，倾向只做灰度 AA。

## ADR-004 排版自己做到什么程度

| 方案 | 影响 | 说明 |
| --- | --- | --- |
| **IDWriteTextLayout 直接用** | 体+++ 复+++ | 免费获得换行、双向、复杂脚本、字体回退；控制力弱（自定义换行策略、行距微调受限） |
| IDWriteTextAnalyzer 自排 | 体-- 复--- | 完全可控（可做逐字测量缓存、增量排版），但要自己处理换行/回退/BiDi，代码量大 |
| 纯自研（不用 DWrite） | — | 抛开 DWrite 需自带字体解析 + 成形，与既定技术栈不符 |

**建议：IDWriteTextLayout 起步**，对热路径（同一文本重复排版）加一层轻量测量缓存；若后续出现 Layout 创建开销瓶颈，再对简单场景走自排。

## ADR-005 UI 模型：保留模式 / 立即模式 / 混合

| 方案 | 影响 | 说明 |
| --- | --- | --- |
| **保留模式**（建议） | 体○ 内+ 性+ 复○ | 元素树 + 脏矩形，空闲时零开销，最契合"空闲不干活" |
| 立即模式（IMGUI） | 体+++ 复+++ | 代码最少，但每帧全量重建 + 全量绘制，与"低 CPU/低内存"目标相悖 |
| 混合（IM 构建 + 保留树 diff） | 体- 复- | 开发体验好，但需引入 diff 与状态复用，复杂度上升 |

**已定：保留模式。**

## ADR-006 布局算法

| 方案 | 影响 | 说明 |
| --- | --- | --- |
| **自研简化 Flex（行/列 + 堆叠 + 绝对 + 网格）** | 体++ 复++ | 覆盖 90% 场景，代码可控 |
| 完整 Flexbox 兼容 | 体- 复-- | 规则与边缘情况多 |
| 约束求解（Cassowary 类） | 体-- 复--- | 表达力强但求解器本身不小 |
| 仅父控件硬编码布局 | 体+++ 复+++ | 最省，但控件复用性差 |

**建议：简化 Flex**（主轴/交叉轴 + 对齐 + 换行？换行待定）+ 堆叠 + 绝对；文本/图片用自然尺寸测量。

## ADR-007 语言特性开关

| 项 | 草案建议 | 理由 |
| --- | --- | --- |
| 异常 | **关闭**（`/EHsc` → `/EHs-c-`） | 体积、代码体积与错误处理显式化 |
| RTTI | **关闭**（`/GR-`） | 控件类型用自定义 TypeId（整数）而非 `typeid` |
| STL | 待定 | 若严格控体积则自实现最小容器；若接受 STL 代码膨胀则限定用 `vector`/`span` 等少数几个 |
| 错误传递 | 待定 | 建议：内部用轻量 `Result<T,E>`（或 `bool` + out 参数），仅在初始化阶段保留详细信息 |
| 多线程 | UI 单线程 | 引用计数用非原子，省体积与开销 |

## ADR-008 CRT 链接方式

| 方案 | 影响 | 说明 |
| --- | --- | --- |
| **静态链接 `/MT`**（建议） | 体++ 复+++ | 交付单文件，无需分发 VC 运行库；体积增量可控（只链入用到的部分） |
| 完全不用 CRT（`/NODEFAULTLIB`） | 体+++ 复--- | 需自实现 `memcpy`/`new`/静态初始化/栈检查等，且与 C++20 特性冲突较多 |
| 动态链接 `/MD` | 体+ | 需随附 VC 运行库，与"无依赖"的观感冲突 |

**建议：`/MT`**，并把"不用 CRT"列为远期可选项而非初期目标。

## ADR-010 窗口形态

| 方案 | 影响 | 说明 |
| --- | --- | --- |
| **普通 HWND 不透明**（建议默认） | 体+++ 性+++ 复+++ | Flip Model 交换链，性能与延迟最优；圆角/阴影需另想办法 |
| 普通 HWND + 自绘圆角（利用 DWM 区域裁剪或自绘到不透明背景） | 体++ 性++ | 由 DWM 处理圆角时需走非公开 API，需评估 |
| `WS_EX_LAYERED` + `UpdateLayeredWindowIndirect` | 性-- | 走 GDI 合成路径，大尺寸窗口下内存拷贝开销明显 |
| DirectComposition（dcomp.dll） | 体- 性++ 复- | 系统组件，属"无依赖"；可拿圆角/阴影/合成动画，但引入视觉树与 IDComposition 复杂度 |

**已定：DirectComposition（dcomp.dll，系统组件）承载窗口。** 圆角/阴影/透明为早期必须能力，故不走普通不透明 HWND 与 Layered Window 路线，直接采用 DComp 视觉树 + D3D11 交换链内容。代价（视觉树管理复杂度、少量内存）在新优先级（功能完备度优先）下可接受。
随之需确定（待定）：圆角/阴影由 DComp 特性提供还是自绘到透明像素；每窗口一个 DComp Device 还是进程级共享。

## ADR-012 线程模型

| 方案 | 影响 | 说明 |
| --- | --- | --- |
| **单线程**（建议） | 体+++ 内++ 复+++ | 消息、布局、绘制同线程，无锁、无跨线程同步开销 |
| UI 线程 + 渲染线程 | 性++ 复-- | 需处理输入竞争与状态快照，收益在复杂场景下才明显 |

**建议：单线程**；仅把"耗时的字体/图片加载与解码"允许放到工作线程，结果回灌到 UI 线程。

## ADR-013 呈现策略

| 项 | 草案建议 |
| --- | --- |
| 交换链 | Flip Model（`DXGI_SWAP_EFFECT_FLIP_DISCARD`） |
| 同步 | 默认 VSync（Present 间隔 1）；高刷/低延迟场景启用 `DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING` + `Present(0, DXGI_PRESENT_ALLOW_TEARING)` |
| 触发 | **按需呈现**：只有在有脏区或动画运行时才进入绘制流程，空闲不 Present |
| 后台缓冲格式 | 待定：`BGRA8UNORM`（便于直接写入颜色，也便于与其它组件互操作）|
| 混合 | 全程 **预乘 Alpha**（premultiplied），避免半透明边缘错误 |

## ADR-014 DPI 与缩放

- DPI 感知级别：**Per-Monitor V2**（若采纳 1703 基线）。
- 内部单位：全部使用 DIP（1/96 英寸），仅在最终呈现时乘缩放系数。
- 缩放档位：整数档（100/125/150/200%）优先；非整数档由系统位图缩放还是自绘缩放 —— **待定**，与 ADR-003 的光栅化方案联动（SDF 可无损支持任意缩放）。

## ADR-016 工程结构

现状：`DUI.vcxproj` 为 Console 应用，源码 `DUI/DUI/main.cpp`。

建议调整为：

```
DUI/                    源码根
  Core/ Platform/ Graphics/ Text/ UI/ App/

Samples/                示例工程（单独 vcxproj）
```

**已定：交付形态为静态库。** 链接器自动裁剪未引用代码，未启用模块不进二进制，最利于体积与集成。

## ADR-018 开发者界面编写方式

**已定：纯 C++ 直接编写界面，不提供 XAML / HTML / CSS 等声明式描述语言。**

- 界面 = C++ 代码组合控件（构造 → 设置属性 → 添加子元素）。无运行时 UI 描述解析器：省体积、省启动开销，界面结构的类型安全由编译期保证。
- 简化写界的手段是**提供大量可高度定制的控件**，而非描述语言。定制点分层：
  1. 属性 / 样式覆盖（颜色、圆角、间距、字号等）
  2. 自定义绘制钩子（接管或追加绘制）
  3. 布局参数（见 ADR-006 的布局模型）
  4. 继承派生新控件
- 待定：是否提供链式 builder 风格 API（`Text("OK").Padding(8).OnClick(fn)`）以压缩样板代码；主题/资源是否需要运行时文件形态。
